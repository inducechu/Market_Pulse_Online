# Два ожидающих запроса на одном carrier thread

## Запуск

JDK 25, команды из корня репозитория. Демо использует только классы JDK, тестовые библиотеки для этого запуска не нужны.

```bash
mvn -pl advanced test-compile
"$JAVA_HOME/bin/java" -Djdk.virtualThreadScheduler.parallelism=1 -Djdk.virtualThreadScheduler.maxPoolSize=1 \
  -cp advanced/target/test-classes academy.backend.market_pulse.portfolio.OneCarrierNetworkDemo
```

1. Запомнить напечатанный PID. Enter запускает P1, сервер удерживает заголовки ответа.
2. Следующий Enter запускает P2. Дождаться `server received P2`, пока P1 всё ещё ждёт.
3. Сравнить `P1 before read` и `P2 before read`: разные ID виртуальных потоков, один carrier thread. Теперь можно снять диагностику.
4. Следующий Enter разрешает ответы. В `after read` ID виртуальных потоков совпадают с их ID до чтения. После HTTP 200 последний Enter завершает демо.

## Что смотреть в коде

[OneCarrierNetworkDemo](../../../src/test/java/academy/backend/market_pulse/portfolio/OneCarrierNetworkDemo.java): `readResponse`, вызов `getResponseCode`. Это обычный блокирующий API; пока сокет ждёт данные, виртуальный поток может освободить carrier. HTTP-сервер работает на отдельных платформенных потоках и не входит в ограничение клиентского планировщика.

Точки останова ставить на вызов `getResponseCode` и на вывод `after read`, с `Suspend: Thread`. Дампы и длительности собирать отдельным запуском без пауз отладчика.

## Диагностика из второго терминала

Подставить PID демо вместо 12345. Снять дамп до разрешения ответов.

```bash
demo_pid=12345
"$JAVA_HOME/bin/jcmd" "$demo_pid" Thread.dump_to_file -overwrite "/tmp/vt-both-$demo_pid.txt"
"$JAVA_HOME/bin/jcmd" "$demo_pid" Thread.vthread_scheduler
"$JAVA_HOME/bin/jcmd" "$demo_pid" Thread.vthread_pollers
```

В дампе найти `demo-vt-P1` и `demo-vt-P2`, ожидание чтения сокета. Планировщик ограничен одним carrier, при этом два клиентских запроса уже приняты сервером. Названия внутренних классов и устройство poller зависят от JVM и ОС.

При необходимости записать JFR: начать перед запуском P1, остановить после выдачи ответов.

```bash
"$JAVA_HOME/bin/jcmd" "$demo_pid" JFR.start name=vt-network settings=profile 'jdk.SocketRead#threshold=0ms'
# После разрешения ответов:
"$JAVA_HOME/bin/jcmd" "$demo_pid" JFR.stop name=vt-network filename="/tmp/vt-network-$demo_pid.jfr"
"$JAVA_HOME/bin/jfr" print --events jdk.SocketRead "/tmp/vt-network-$demo_pid.jfr"
```

Искать клиентские `eventThread` с именами `demo-vt-P1` и `demo-vt-P2`. По `startTime` и `duration` видно перекрытие ожиданий чтения. Событие появляется после завершения чтения; в записи будут и серверные события. JFR SocketRead не показывает точные моменты mount/unmount.

## Проверка на прикладном клиенте

```bash
mvn -pl advanced -Dtest=OneCarrierTest test
```

Тест стартует отдельную JVM с одним carrier, удерживает ответ P1 и проверяет поступление P2 до его освобождения. Обе оценки после выдачи ответов дают 2100 RUB. Это воспроизводимая проверка конкурентного ожидания сети, а не бенчмарк производительности.


## Результаты проверки

Проверено на JBR 25.0.3. Идентификаторы потоков и порядок получения ответов между запусками могут различаться.

| Кейс | Что проверяли | Результат |
|---|---|---|
| Два удержанных ответа | P2 принят до выдачи ответа P1 | Оба запроса дошли до сервера; `parallelism=1 poolSize=1`; оба завершились HTTP 200 |
| Три движка через HTTP mock | P1 и P2 через FUTURE, CF и VT | Каждый вариант вернул по 2100 RUB в порядке ввода |
| Ошибка и резерв | HTTP 503 у основного поставщика | Без политики - ошибка; с BACKUP_ON_503 каждый движок вернул по 2460 RUB |

Вывод ограничен проверенными сценариями: один carrier позволяет перекрывать ожидание сетевых ответов, а выбор оркестрации не меняет результат расчёта. Производительность и длительности mount/unmount этим прогоном не измерялись.
