# Два ожидающих запроса на одном carrier thread

## Запуск

Из корня репозитория, на JDK 25. Демо поднимает свой HTTP-сервер на свободном локальном порту.

```bash
mvn -pl advanced -am compile
java -Djdk.virtualThreadScheduler.parallelism=1 -Djdk.virtualThreadScheduler.maxPoolSize=1 \
  -cp advanced/target/classes academy.backend.market_pulse.demo.concurrency.OneCarrierNetworkDemo
```

1. Запомните напечатанный PID. Нажмите Enter. Сервер напечатает `server received P1` и удержит ответ.
2. Спросите, сможет ли P2 попасть на сервер при одном carrier thread. Нажмите Enter ещё раз. Дождитесь `server received P2` и строки `parallelism=1 poolSize=1`.
3. Остановитесь на приглашении разрешить ответы. В этот момент оба запроса уже на сервере, оба виртуальных потока ждут заголовки ответа. Здесь удобно снять дамп.
4. Нажмите Enter. Оба клиента получат HTTP 200. Сравните идентификатор до и после чтения отдельно для P1 и P2. Последний Enter завершит демо.

## Что открыть в IDE

В [OneCarrierNetworkDemo](../../../src/main/java/academy/backend/market_pulse/demo/concurrency/OneCarrierNetworkDemo.java) комментарии `NOTICE` стоят рядом с точками наблюдения. В `readResponse` поставьте брейкпоинты на вызов `getResponseCode()` и вывод `after read`. Для обоих выберите **Suspend: Thread**, чтобы пауза в клиенте оставляла серверу возможность отвечать. Посмотрите `id`, `Thread.currentThread().threadId()`, `Thread.currentThread().isVirtual()` и значение `status` после чтения. Между остановами нажимайте Resume.

Ограничение в один carrier действует на клиентские виртуальные потоки. Сервер обслуживает запросы на двух отдельных платформенных потоках. Строка `server received P2` появляется в консоли, пока сервер ещё удерживает ответ P1.

## Что посмотреть во втором терминале

Для дампа или записи времени запустите демо без брейкпоинтов. Подставьте PID, который оно вывело.

```bash
demo_pid=12345
jcmd "$demo_pid" Thread.dump_to_file -overwrite "/tmp/vt-both-$demo_pid.txt"
jcmd "$demo_pid" Thread.vthread_scheduler
jcmd "$demo_pid" Thread.vthread_pollers
```

В дампе найдите `demo-vt-P1` и `demo-vt-P2`. Оба стека ведут от `readResponse` в сетевое чтение. Названия внутренних методов зависят от сборки JDK и ОС. Вспомните, что происходит на слайдах 47 и 48. Готовность сокета даёт возможность возобновить виртуальный поток. К пользовательскому коду он вернётся, когда получит carrier.

Если осталось время, запишите JFR. Начните перед первым запросом и остановите после получения ответов, пока демо ждёт последнего Enter.

```bash
jcmd "$demo_pid" JFR.start name=vt-network settings=profile 'jdk.SocketRead#threshold=0ms'
jcmd "$demo_pid" JFR.stop name=vt-network filename="/tmp/vt-network-$demo_pid.jfr"
jfr print --events jdk.SocketRead "/tmp/vt-network-$demo_pid.jfr"
```

Найдите события чтения с `eventThread` обоих клиентов и сравните их интервалы ожидания. Для проверки того же эффекта на клиенте портфелей запустите `mvn -pl advanced -Dtest=OneCarrierTest test`. Тест ждёт поступления обоих запросов до освобождения первого и проверяет обе итоговые оценки по 2100 RUB.
